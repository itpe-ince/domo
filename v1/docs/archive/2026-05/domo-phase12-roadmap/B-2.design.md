## 1. 목표 및 Acceptance Criteria

### 목표

기존 Phase 8~10에 걸쳐 개별 목적으로 구축된 분석 인프라(코호트 retention 알림, newsletter 이벤트 추적, ML 실험 결과, AI 기능 사용 로그)를 Admin 콘솔 단일 페이지에 통합한다. 운영자가 별도 DB 쿼리 없이 그로스 해킹 의사결정에 필요한 4개 핵심 지표를 한 화면에서 확인하는 것이 목표다.

### Phase 12 B-2가 중요한 이유

Phase 11까지 analytics 데이터는 존재했지만 운영자가 접근할 방법이 없었다:
- `cohort_alerts` 테이블 (0072 alembic) — Slack 알림 전송에만 사용
- `newsletter_events` 테이블 (0067 alembic) — 집계 없이 원시 이벤트만 저장
- `ml_experiment_assignments` + `post_engagement_cache` — A/B 결과는 `/admin/experiments`에서 실험 단위만 표시
- AI 캡션/도슨트/컬렉션 사용률 — DB에 존재하나 어디서도 집계되지 않음

B-2는 이 데이터들을 처음으로 운영자에게 가시화한다.

### Acceptance Criteria

| 항목 | 기준 |
|------|------|
| `/admin/analytics` 페이지 접근 | 2FA 인증 admin만 가능 (미인증 → 401/403) |

## 5. PostHog 임베드 Hybrid 전략

### 동작 원리

```
NEXT_PUBLIC_POSTHOG_INSIGHTS_BASE_URL 환경변수
  ├── 설정됨  → PostHog iframe 렌더링 (우선)
  │             src: `${BASE_URL}/embedded/{dashboardId}`
  │             sandbox="allow-scripts allow-same-origin"
  │             CSP 차단 시: onError → SVG 차트 fallback 전환
  └── 미설정  → 자체 SVG 차트 (백엔드 endpoint 호출)
```

### PostHog iframe 적용 대상

B-2에서는 4개 카드 중 SVG 차트를 우선 구현하고, PostHog 임베드는 `CohortRetentionCard`와 `NewsletterOpenRateCard` 두 카드에만 iframe fallback을 제공한다. Feed CTR과 AI 사용률은 PostHog에 별도 대시보드가 없으므로 항상 자체 SVG 차트 사용.

### env 변수

```bash
# v1/admin/.env.local
NEXT_PUBLIC_POSTHOG_INSIGHTS_BASE_URL=https://us.posthog.com/shared  # 선택
```

## 6. 백엔드 API 설계

### 공통 규칙

- 모든 endpoint: `require_admin_with_2fa` 의존성 (기존 패턴 유지)
- `period` 쿼리 파라미터: `"7d" | "30d" | "90d"` (기본값 `"30d"`)

### 6-1. GET /admin/analytics/cohort-retention

```sql
-- cohort_alerts에서 d7/d30 retention 값 시계열 조회
SELECT
  cohort_date,
  MAX(CASE WHEN metric_name = 'd7_retention' THEN value END)  AS d7,
  MAX(CASE WHEN metric_name = 'd30_retention' THEN value END) AS d30
FROM cohort_alerts
WHERE cohort_date >= CURRENT_DATE - :days
  AND status = 'sent'
GROUP BY cohort_date
ORDER BY cohort_date ASC;
```

### 6-2. GET /admin/analytics/newsletter-open-rate

**데이터 소스**: `newsletter_events` 테이블 (0067 alembic) + `newsletter_issues` 테이블

**쿼리 전략**:
```sql
-- 발송일 기준 집계 (newsletter_issues.sent_at 날짜 그룹)
SELECT
  DATE(ni.sent_at AT TIME ZONE 'UTC') AS sent_date,
  COUNT(DISTINCT ni.id)               AS issues_sent,
  COUNT(DISTINCT CASE WHEN ne.event_type = 'open'  THEN ne.user_id END) AS unique_opens,
  COUNT(DISTINCT CASE WHEN ne.event_type = 'click' THEN ne.user_id END) AS unique_clicks,
  COUNT(DISTINCT ni.subscriber_count) AS total_recipients
FROM newsletter_issues ni
LEFT JOIN newsletter_events ne ON ne.issue_id = ni.id
WHERE ni.sent_at >= NOW() - INTERVAL :days DAY
  AND ni.sent_at IS NOT NULL
GROUP BY sent_date
ORDER BY sent_date ASC;
```

### 6-3. GET /admin/analytics/feed-ctr

**데이터 소스**: `ml_experiment_assignments` + `post_engagement_cache`

**쿼리 전략**:
```sql
-- algo별 post 노출 수 대비 engagement 클릭 수 근사 CTR
-- ml_experiment_assignments: user_id + variant_name + created_at
-- post_engagement_cache: post_id + engagement_score + calculated_at
-- CTR 근사: variant별 사용자 평균 engagement_score 사용
SELECT
  mea.variant_name AS algo,
  COUNT(DISTINCT mea.user_id) AS users,
  AVG(pec.engagement_score) AS avg_engagement,
  -- CTR 근사: engagement > 0인 post 비율 / 전체 post
  COUNT(DISTINCT CASE WHEN pec.engagement_score > 0 THEN pec.post_id END)::float
    / NULLIF(COUNT(DISTINCT pec.post_id), 0) AS ctr_approx
FROM ml_experiment_assignments mea
JOIN post_engagement_cache pec
  ON pec.calculated_at >= NOW() - INTERVAL :days DAY
WHERE mea.created_at >= NOW() - INTERVAL :days DAY
  AND mea.experiment_id IN (
    SELECT id FROM ml_experiments WHERE name LIKE '%feed%'
  )
GROUP BY mea.variant_name
ORDER BY mea.variant_name;
```

**응답 형식**:
```json
{
  "data": {
    "algos": [
      { "name": "default", "ctr": 0.029, "user_count": 412 },
      { "name": "v1",      "ctr": 0.038, "user_count": 208 },
      { "name": "v2",      "ctr": 0.051, "user_count": 215 }
    ],
    "summary": {
      "best_algo": "v2",
      "delta_v2_vs_v1": 0.013
    }
  },
  "cached_at": "2026-05-08T13:00:00Z"
}
```

**참고**: feed 알고리즘 실험명 필터(`name LIKE '%feed%'`)는 `ml_experiments` 실제 데이터에 맞게 구현 시 조정.

## 7. Redis 5분 캐시 구현 패턴 (백엔드)

모든 4개 endpoint에 동일한 패턴 적용:

```python
# app/api/admin_analytics.py (신규)

import json
from datetime import datetime, timezone
from app.core.redis import get_redis  # 기존 Redis 클라이언트

CACHE_TTL = 300  # 5분

async def _get_cached_or_compute(
    cache_key: str,
    compute_fn,  # async callable → dict
) -> dict:
    """Redis 캐시 조회 → miss 시 compute_fn 실행 → 저장."""
    redis = await get_redis()

    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)

    result = await compute_fn()
    result["cached_at"] = datetime.now(timezone.utc).isoformat()

    await redis.setex(cache_key, CACHE_TTL, json.dumps(result))
    return result


@router.get("/admin/analytics/cohort-retention")
async def get_cohort_retention(
    period: str = "30d",
    db: AsyncSession = Depends(get_db),
    _admin = Depends(require_admin_with_2fa),
):
    days = {"7d": 7, "30d": 30, "90d": 90}.get(period, 30)
    cache_key = f"admin:analytics:cohort_retention:{period}"

    async def compute():
        return await _query_cohort_retention(db, days)

    data = await _get_cached_or_compute(cache_key, compute)

    from fastapi.responses import JSONResponse
    response = JSONResponse(content={"data": data["data"]})
    response.headers["X-Cache-At"] = data.get("cached_at", "")
    response.headers["Cache-Control"] = f"max-age={CACHE_TTL}"
    return response
```

캐시 수동 갱신: 프론트엔드 "새로고침" 버튼은 `?bust=1` 쿼리 파라미터를 추가하고, 백엔드는 이 파라미터 존재 시 캐시를 강제 갱신(기존 key delete → recompute → setex).
